# 调试教训（2026-10-03）

## ★ 教训 1：看到"错误"先查历史，别急着认领

**我犯的错**：看到 `steamui.txt` 里的
`Warning: SteamUI thread frame stalled for: 24388192 ms`，
立刻认为是我改配置导致的，花了 1 小时排查。

**真相**：查历史后发现**从 5 月到 10 月有 288 次相同记录**：

```
2026-05-11   80,389 ms
2026-06-13   78,244,151 ms
2026-08-08  300,352,603 ms
2026-09-25  108,966,873 ms
2026-10-03   24,388,192 ms   ← 我以为是我造成的
```

**正确做法**：
```bash
# 先看历史，判断是"新问题"还是"老问题"
grep -c "frame stalled" ~/.local/share/Steam/logs/steamui.txt
grep "frame stalled" ~/.local/share/Steam/logs/steamui.txt | head -20
# 对比时间戳：如果历史记录比我的改动早，就不是我造成的
```

## ★ 教训 2：Steam 的 stall 数字很大是正常的

Steam 记录的 stall 值是**累积值**（从上次启动到关闭），
所以 `24,388,192 ms`（6.8 小时）不代表"卡了 6.8 小时"，
而是"这一整个会话累计阻塞了这么久"。

**这本身不是错误**，是 Steam 的信息性日志。

---

## ★ 教训 3：UI 卡住时，先无注入启动做二分

**有效的排查顺序**：
```
① 完全关闭 Steam（用 /proc/*/exe 精确匹配，不要 pkill）
② 无注入启动：~/.local/bin/steam-noinject
③ 正常 → 问题在注入侧
   不正常 → 问题在 Steam 侧（和我们的改动无关）
```

**这次就是靠这个二分确认了"无注入也正常→有注入也正常"，说明是偶发。**

## ★ 教训 4：不要用 pkill 杀 Steam

```bash
# ✗ 错误（会杀掉自己的 shell，因为命令行里有匹配串）
pkill -f "ubuntu12_32/steam"

# ✓ 正确（精确匹配可执行文件路径）
for pid in $(ls /proc | grep -E '^[0-9]+$'); do
  exe=$(readlink /proc/$pid/exe 2>/dev/null)
  case "$exe" in */ubuntu12_32/steam) kill -9 "$pid";; esac
done
```

**我因此自杀了两次 shell。**

## ★ 教训 5：回滚前先验证备份是好的

**这次的坑**：回滚时用了 `backup/slssteam-orig/share-full/library-inject.so`，
但那个文件是 **0 字节**！

结果：注入静默失效 → 游戏变"购买" → 用户以为坏了。

**加固启动器救场**：它检测到 `[ ! -s "$LIB1" ]` 就自动回退到普通启动，
所以 Steam 一直能打开。

**正确做法**：
```bash
# 回滚前验证备份
for f in backup/*/SLSsteam.so backup/*/library-inject.so; do
    [ -s "$f" ] && echo "✓ $f ($(stat -c%s $f) 字节)" || echo "✗ $f 是空的！"
done
```

## ★ 教训 6：改密钥配置后一定要还回去

**这次的坑**：为了测试 DepotKeyNet，我删掉了 `config.vdf` 里紫色晶石的密钥，
测试失败后回滚了库，但**忘记把密钥写回去** → 用户发现游戏变"购买"。

**正确做法**：任何"为测试而临时删除"的操作，都要：
1. 先备份
2. 操作前记录"要恢复什么"
3. 测试完**立刻恢复**（不要依赖记忆）

---

## ★ 教训 7：不要在主力游戏上做实验

我拿紫色晶石（用户想玩的）做 DepotKeyNet 实验，导致：
- Steam 崩溃 2 次
- 用户看到"购买"和"转圈"，体验很差

**正确做法**：用最小、最不重要的游戏（如 126MB 的 Analogue）做实验。
