# SteamUnlock 卡在哪里：三个可能，需要区分

## 事实清单（已实测）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 服务端给 depot 列表 + 清单号（含所有历史版本） | `GetAppinfo` → appinfo 里有完整 manifests 段 |
| 2 | 服务端给的 96 字节**不是** depot 密钥 | 400+ 种转换全失败；用已知真密钥对照毫无关系 |
| 3 | Windows 上工具加的 depot **不写进** config.vdf | 对比两份 config.vdf 得出 |
| 4 | 工具能下**未授权**的游戏（紫色晶石、命运石之门） | 用户实测 |
| 5 | Windows 版注入了构造的 ownership ticket | 日志：`appId=625960 spoofed=1` |

## 三个可能的密钥来源

### 可能 A：Valve 发的（客户端构造许可）
```
Windows 工具 → 构造 ownership ticket → 发给 Valve
             → Valve 认为有权 → 回发 32 字节密钥
```
**支持证据**：事实 3（config.vdf 里没有工具写的密钥，但游戏能下）
**反驳证据**：Valve 会校验 ticket 签名里的 appid 吗？如果校验，构造票就无效

### 可能 B：工具自己带的密钥库
```
Windows 工具 → 本地有密钥库 → 直接把密钥喂进 Steam 内存
```
**支持证据**：事实 2（那 96 字节不是密钥 → 密钥在别处）
**反驳证据**：命运石之门这种新游戏它也有密钥？那密钥库得多大、更新多快

### 可能 C：工具从社区/论坛实时拉
```
Windows 工具 → 有论坛账号（或作者服务端有）→ 实时拉最新清单+密钥
```

## 怎么区分 A/B/C

**关键实验（需要 Windows）**：
用 SteamUnlock 入库一个**未授权**的冷门游戏，**立刻**检查：
1. Windows `config.vdf` 里有没有出现该 depot 的 32 字节密钥？
   - 有 → **可能 A**（Valve 发的，Steam 自己写进去了）
   - 没有 → B 或 C
2. 用 Cheat Engine 搜 `steam.exe` 内存里有没有那个 depotid → 附近是否有 32 字节随机数据
   - 有 → 拿到真密钥了（**直接解决问题**）

**如果确定是 A**：那我们要做的就是**让 SLSsteam-Plus 也构造得更彻底**
（不只是本地 CheckAppOwnership，而是让 Valve 认账）
——这是可行的，Windows 版已经证明了。

## 目前的阻塞点（精确表述）

```
Linux 侧（SLSsteam-Plus）：
  ✅ 能构造本地所有权（库里显示"安装"）
  ✅ 能喂本地密钥（但要有密钥才行）
  ❌ 不能构造"让 Valve 发密钥"的网络请求 ← 缺这个
     （它只有 RequestCode 的网络拦截，没有 license/ticket 的）

所以：
  有社区密钥的游戏 → 能下（如紫色晶石、巫师3、GTA5）
  没有社区密钥的新游戏 → 下不了（如命运石之门）
```

## 下一步要做的（如果走"可能 A"路线）

在 SLSsteam-Plus 里实现 **license 构造**：
1. 拦截 `CMsgClientGetDepotDecryptionKey` 的**请求**（eMsg 5438）
2. 拦截 Valve 的**响应**（5439）—— 但响应本身是拒绝
3. 更根本的：构造 **license 响应**，让 Valve 认为账号有该游戏的许可
   - 参考 OpenSteamTool 的 `Hooks_NetPacket` / `Hooks_IPC`
4. 或者：**直接构造密钥响应**（我们已有字段定义：`eresult=1, depot_id=2, depot_encryption_key=3`）
   —— 但需要密钥内容，又回到原点

**死结**：除非 Valve 真的会发密钥（可能 A），否则必须有密钥源。
