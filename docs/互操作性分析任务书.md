# 二进制互操作性分析任务书

> 目标：理解第三方 Steam 扩展组件的**数据格式与文件布局**，
> 以便本项目（`Steam Toolkit`）能够**正确读取和兼容**这些格式。
>
> 分析对象为已获取的二进制文件样本，全程静态分析。
> 输出要求：格式描述 + 算法说明 + 证据（偏移/反汇编片段），**不需要实现代码**。

---

## 背景

Steam 生态里存在若干第三方客户端扩展方案，它们各自定义了自己的
**配置持久化格式**（插件文件、清单文件、键值文件）。

这些格式目前**没有公开规范**，导致：

- 本项目的配置读取器无法解析他人写的插件文件（互操作缺口）
- 用户从其他方案迁移过来时，历史配置无法被识别
- 我们无法验证自己写出的文件是否符合社区既有格式

本任务书要求**还原这些格式的规范**，属于典型的格式逆向与互操作性工作。

本项目自身的实现路径是**公开透明的配置管理**（写入 Steam 官方
支持的 `config.vdf` / `.manifest` / Lua 配置目录），与这些第三方组件
的关系是"**读取兼容**"，不是"复用其加载机制"。

## 任务 A：插件文件（`.o`）容器格式

### 样本

| 项目 | 值 |
|---|---|
| 文件名 | `Console.dll` |
| 大小 | 133,632 字节 |
| SHA-256 | `aba066c06794b567ffa4458c0b980a5da65fbfa81da2cbae70b7d63b38658198` |
| 类型 | PE32+ DLL，x86-64，6 节 |
| 导出 | `AddAppid` / `DelAppid` / `LuaScript` / `launch_steam` |
| 导入 | 仅 `KERNEL32.dll` + `WS2_32.dll` |
| 本地路径 | `/home/deck/.dsh/attachments/v1/files/ab/aba066c0…/Console.dll` |

### 已有事实（本项目独立验证，不是推测）

1. `.o` 插件文件是**文本经过编码后**落盘的容器，扩展名 `.o`，位于
   插件目录下。
2. 解码后的文本形如：

   ```
   addappid(APPID)
   addtoken(APPID, "<token>")
   addappid(DEPOT, 1, "<192 hex>")
   setManifestid(DEPOT, "<gid>", <size>)
   ```

3. 我们已能解出 5 个真实样本（`108600` / `294100` / `625960` / `977950` / `AppInfos`），
   全部呈现 `<192 hex>`（96 字节）的第 3 个参数。
4. **关键未知**：Steam 客户端真正需要的 depot 密钥是 **32 字节（64 hex）**。
   我们已实测：96 字节值里**不包含**这 32 字节（前 64 / 后 64 / 任意偏移均不匹配，
   5 个 depot 交叉验证）。

### 需要回答的问题

| # | 问题 | 期望输出 |
|---|---|---|
| A1 | `Console.dll!AddAppid` 的输入是什么形态？（整段文本？还是结构体？） | 参数类型 + 调用约定 |
| A2 | `<192 hex>` 这个值在 `AddAppid` 内部**被怎么处理**？ | 反汇编关键片段 + 调用链 |
| A3 | 它最终**交给谁**？（自身转换 / `steamclient64.dll` 导出 / IPC） | 目标模块 + 函数名/序号 |
| A4 | 若是自身转换：**算法是什么**？ | 算法描述（步骤、常量、是否有 KDF/哈希/分组密码） |
| A5 | 192 hex 与 64 hex 的**语义关系**：是否有一个字节区间是"校验/元数据"，另一个是有效载荷？ | 字段布局表 |

**只要 A2–A4 有结论，A5 自然得出。**

### 提示（减少无效搜索）

- 该 DLL 只导入 `KERNEL32` + `WS2_32` → 若做加密，必然是**自实现**或调用 SDK。
- 文件很小（130 KB），`.text` 段仅约 71 KB → 反汇编可行。
- 关注 `AddAppid` 里对十六进制字符串的解析（常见形态：`strtoul` 循环、
  逐 2 字符转字节、查表）。

## 任务 B：注入组件的文件布局与配置读取

### 样本

| 项目 | 值 |
|---|---|
| 内部名 | `dwmapi.dll`（同名代理） |
| 大小 | ~650 KB，PE32+ x86-64 |
| SHA-256（按节切出） | `A42462DE1BADE30E7B77B28CE4C2DD61AE6B327A22F02043A43FD70DC80C3E4A` |
| 所在位置 | 内嵌于 `Main.dll` 偏移 `0x500253f`（MZ 头） |
| 已知内含 | `cpp-httplib/0.56.0`、`WS2_32`、明文串 `auth1.caigamer.cn`、`steamclient64.dll`、路径模板 `{}\bin\{}`、`GUI`/`GUIMD5` |

### 已有事实

- 该组件部署到 Steam 根目录，通过 **DLL 搜索顺序**被 Steam 进程加载，
  并把真实系统调用转发回系统同名 DLL（保证宿主正常运行）。
- 它**独立联网**（`cpp-httplib`），不经过宿主程序。

### 需要回答的问题

| # | 问题 | 期望输出 |
|---|---|---|
| B1 | 它读取**哪些配置文件**？（路径模板展开后的完整列表） | 路径清单 + 读取顺序 |
| B2 | 它对读到的配置做什么**解析**？（格式、字段名） | 结构描述 |
| B3 | 它是否也处理**插件文件**？如果是，处理逻辑与任务 A 是否同一套？ | 是/否 + 对比 |
| B4 | `GUIMD5` 的具体用途（校验对象、算法、比对方式） | 说明 |
| B5 | 它访问远端的目的与**请求/响应格式**（只看格式，不看内容） | 端点 + 报文结构 |

### 为什么问 B5

本项目需要判断：**这些远端接口是否有公开替代**。
如果只是"取数据"，本项目已有等价公开数据源；如果是"授权校验"，则与
本项目的透明配置管理路线无关，我们只需知道边界在哪里。

## 任务 C：主机侧密钥数据的存储形态（**最高优先级**）

### 动机（纯技术）

Steam 客户端在下载受保护内容时，会先获得 **32 字节的 depot 解密密钥**，
该密钥在客户端进程内以某种形态存在。理解**这个存储形态**，本项目就能：

- 校验自己写入的配置是否被客户端正确接受
- 为用户**自己已授权的游戏**提供本地一致性检查
- 在格式层面与官方客户端对齐（互操作性）

**注意**：本任务的对象是 **Steam 客户端自身的行为**，
不是任何第三方工具。

### 需要回答的问题

| # | 问题 | 期望输出 |
|---|---|---|
| C1 | 32 字节密钥在客户端内存中**以什么形态存放**？（裸字节 / 结构体字段 / 密钥调度中间态） | 结构描述 + 依据 |
| C2 | 是否有**可静态识别的特征**？（如定长数组、指针表、已知常量、vtable 关联） | 特征描述 |
| C3 | 从"密钥字节"到"可用于解密的形态"经过**哪些步骤**？（若涉及密钥扩展，说明算法与轮数） | 步骤 + 算法 |
| C4 | 该数据与 `config.vdf` 里 `Depots/<id>/DecryptionKey` 字段的关系：是否**同一份数据的两种表示**？ | 是/否 + 转换关系（若有） |
| C5 | Linux 客户端（`steamclient.so`）与 Windows 客户端在此处的**差异**（若有） | 差异点 |

### 已知线索

- 本项目在 Linux 上实测：把 64 hex 写进 `config.vdf` 的
  `Software/Valve/Steam/Depots/<depotid>/DecryptionKey` 后，
  客户端在启动时读取，下载流程正常。
- 说明该字段**就是**客户端接受的输入形态之一。
- C4 要回答的是：**内存态**与**文件态**是否一致，或存在派生关系。

## 方法建议

| 场景 | 建议手段 |
|---|---|
| 小文件全反汇编 | `objdump -d` / `radare2` / IDA-free 均可 |
| 定位关键函数 | 从导出表 (A) 或字符串交叉引用 (B) 入手 |

## 范围声明

本任务书要求的是**静态格式分析**：文件布局、字段语义、算法描述。

**不包含**：
- 编写绕过任何授权校验的工具
- 复用第三方组件的加载/注入机制
- 获取或分发受版权保护的内容

本项目自身的路线是**在用户目录内管理公开可验证的配置数据**，
本次分析的目的仅在于**读懂既有格式以实现互操作**。
