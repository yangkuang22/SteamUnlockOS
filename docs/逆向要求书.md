# 逆向要求书 — SteamTools `.o` 密钥格式

> 目标：把 SteamTools/stplug-in 的 48 字节"密钥"值还原成 Steam 真正需要的 32 字节 depot 解密密钥。
> 这是唯一的阻塞点。解开它，SteamUnlock 的全部数据就能接入我们的 Linux 实现。

## 0. 背景与已确认事实

### 已确认（无需重复验证）

| 项目 | 值 | 验证方式 |
|---|---|---|
| 数据格式 | `Steam\config\stplug-in\<appid>.o` | 实际文件 |
| 加密 | **RC4，密钥 = 20 字节** | 4 个 `.o` 文件 RC4 解密后 100% 可打印 |
| RC4 密钥 | `a1fca1fca1fdfda1fba1faa1fba1fa42414241` | hex；GBK 解码 = `↑↑↓↓←→←→BABA` |
| 解密后格式 | 与 SteamTools Lua 完全一致的文本 | 见下 |
| 密钥来源 | `http://auth1.caigamer.cn/GetAppinfo/<appid>` | 实测有数据（含 4012810） |
| 该 API 的外层加密 | 同一把 RC4 密钥 | 实测解密成功 |

`.o` 解密后的实际内容样本（appid 625960，紫色晶石）：

**关键观察**：`addappid(DEPOT, 1, "<96 hex>")` —— 这个 hex 是 **48 字节**，
而 Steam 的 depot 解密密钥是 **32 字节**（AES-256）。
签名 `1` 在 SteamTools 语义里表示"这是特殊格式的密钥"。

### 已排除的假设（不要重复）

- ✗ 32 字节真密钥出现在 48 字节值的任何窗口偏移
- ✗ `XOR` 固定掩码（用两个 depot 的 XOR 关系验证失败）
- ✗ 前 32 / 后 32 / 中间 32 字节直接切片
- ✗ AES-ECB/CBC 用 `md5(RC4KEY)` / `sha256(RC4KEY)` 当密钥解密
- ✗ 服务器值随每次请求变化（同 depot 两次请求结果一致 → 是确定性函数）

## 1. 核心问题（唯一需要解答的）

**48 字节值 → 32 字节 Steam depot 解密密钥 的确定性映射算法是什么？**

需要明确的答案：

3. 48 字节的内部结构是什么（例如 16 字节 IV + 32 字节密文 / 或者别的）？

## 2. 建议的切入路径（按性价比排序）

### 路径 A：反汇编 Console.dll（最推荐）

**我们已经有的样本**：`Console.dll`（133 KB，SHA-256 `aba066c0…` 开头）

它在 `Steam\bin\Console.dll`，是 SteamTools 加载 `.o` 的加载器。
**加载器必须做"48 字节 → 32 字节"的转换**，算法就在里面。

具体找法：
- 反汇编，找引用 `DecryptionKey` / `addappid` 的函数
- 找 RC4 实现（20 字节密钥的 RC4 KSA/PRGA 特征：256 字节 S 盒初始化循环）
- 找对 96 字符 hex 字符串的处理（可能先 `strlen == 96` 判断）
- 找 AES 常量：AES 的 S-box 前 16 字节是 `63 7c 77 7b f2 6b 6f c5 30 01 67 2b fe d7 ab 76`；
  或者 AES-256 密钥扩展的 `Rcon` 常量 `01 02 04 08 10 20 40 80 1b 36`
- 注意可能有第二次异或/查表（自定义混淆而非标准 AES）

### 路径 B：动态观察（如果能执行程序）

在隔离环境运行时，hook 掉最终写入 Steam 的位置：
- `Steam\config\config.vdf` 写入时抓密钥
- 或者 hook `steamtools` 进程里"48字节→32字节"转换函数的输入输出
- 比静态分析快，但需要执行程序

### 路径 C：从 SteamTools 官方渠道找

- SteamTools 官方论坛/文档对 `.o` 格式的说明
- `stplug-in` 目录的格式文档
- 注意：不要下载来路不明的二次打包版本
